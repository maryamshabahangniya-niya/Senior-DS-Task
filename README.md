# اولویت‌بندی لیدهای تیم Telesales

هدف این پروژه اینه که با توجه به محدودیت ظرفیت تماس تیم Telesales، مشخص کنیم کدوم لیدها برای تماس در اولویت بالاتری قرار می‌گیرن. داده‌ها مربوط به کاربرهایی هستن که فرایند خرید آنلاین بیمه رو کامل نکردن.

برای این کار، ابتدا احتمال تکمیل خرید هر لید رو با مدل یادگیری ماشین تخمین می‌زنیم. بعد این احتمال رو با حاشیه سود موردانتظار و یک ضریب ساده برای فوریت انقضای بیمه ترکیب می‌کنیم و به هر لید امتیاز و سطح اولویت می‌دیم.




## ساختار پروژه

```text
.
├── data/                  # فایل‌های ورودی
├── src/
│   ├── ingest.py          # ورود داده به PostgreSQL
│   ├── eda.py             # بررسی اولیه داده‌ها
│   ├── train.py           # آموزش و مقایسه مدل‌ها
│   └── score.py           # امتیازدهی و ذخیره خروجی
├── charts/
│   ├── eda/
│   ├── evaluation/
│   └── priority/
├── models/                # مدل ذخیره‌شده
├── reports/               # گزارش‌ها و متادیتا
├── Dockerfile
├── docker-compose.yml
├── requirements.txt
└── README.md
```

## اجرای پروژه

برای اجرا به Docker و Docker Compose نیاز داریم. دستورها باید از پوشه اصلی پروژه اجرا بشن.

ابتدا دیتابیس رو بالا میاریم و ایمیج Pipeline رو می‌سازیم:

```bash
docker-compose up -d db
docker-compose build pipeline
```

بعد اسکریپت‌ها رو به‌ترتیب اجرا می‌کنیم:

```bash
docker-compose run --rm pipeline python src/ingest.py
docker-compose run --rm pipeline python src/eda.py
docker-compose run --rm pipeline python src/train.py
docker-compose run --rm pipeline python src/score.py
```

در تنظیمات فعلی، PostgreSQL روی پورت `5433` سیستم میزبان در دسترسه و کانتینر Pipeline از نام سرویس `db` و پورت `5432` استفاده می‌کنه. اطلاعات اتصال داخل فایل‌های پروژه صرفاً برای اجرای محلی تسک هستن.

## آماده‌سازی داده و EDA

داده اولیه ۵۰٬۱۸۰ ردیف داره، ولی تعداد لیدهای یکتا ۵۰٬۰۰۰ تاست. برای لیدهای تکراری، رکوردی که `Created At` قدیمی‌تری داره نگه داشته می‌شه.

از تاریخ ایجاد لید، ساعت و روز هفته رو استخراج می‌کنیم. مقدار هدف `Completed Purchase` هست و نشون می‌ده خرید تکمیل شده یا نه.

در EDA توزیع متغیرها، داده‌های Missing و نرخ تبدیل در گروه‌های مختلف بررسی شده. نمودارها در `charts/eda/` قرار می‌گیرن.

## آموزش مدل

سه روش رو مقایسه می‌کنیم:

- **Logistic Regression:** برای ویژگی‌های عددی، جایگزینی Missing و Scaling؛ برای ویژگی‌های دسته‌ای، جایگزینی Missing و One-Hot Encoding.
- **LightGBM One-Hot:** جایگزینی Missing و One-Hot Encoding، بدون نیاز به Scaling ویژگی‌های عددی.
- **LightGBM Native:** استفاده مستقیم از ستون‌های دسته‌ای با نوع `category` در Pandas، بدون One-Hot Encoding.

داده با نسبت ۷۰٪ آموزش، ۱۵٪ اعتبارسنجی و ۱۵٪ تست تقسیم می‌شه. انتخاب مدل بر اساس نتایج Validation انجام می‌شه و Test برای ارزیابی نهایی کنار گذاشته می‌شه.

متریک‌های اصلی گزارش‌شده شامل Average Precision، ROC-AUC، Brier Score و معیارهای Top-K هستن. هدف از Top-K اینه که عملکرد رتبه‌بندی رو متناسب با ظرفیت محدود تماس بررسی کنیم.

خروجی‌های این مرحله شامل فایل مدل در `models/`، نتایج مقایسه در `reports/` و نمودارهای ارزیابی در `charts/evaluation/` هستن.

## امتیازدهی لیدها

بعد از آموزش، اسکریپت `score.py` مدل ذخیره‌شده رو بارگذاری می‌کنه و احتمال خرید هر لید رو به دست میاره.

امتیاز اولویت فعلی از این رابطه محاسبه می‌شه:

```text
priority_score = purchase_probability * expected_margin * urgency_weight
```

ضریب فوریت بر اساس تعداد روزهای باقی‌مانده تا انقضای بیمه در نظر گرفته شده:

| وضعیت انقضا | ضریب |
|---|---:|
| تاریخ انقضا گذشته | 1.20 |
| ۰ تا ۷ روز | 1.15 |
| ۸ تا ۱۵ روز | 1.08 |
| سایر موارد یا مقدار نامشخص | 1.00 |

این ضرایب در حال حاضر فرض‌های اولیه بیزنسی هستن و از داده بهینه‌سازی نشده‌ان.

بعد از مرتب‌سازی لیدها بر اساس امتیاز، ۲۰٪ اول در گروه `High`، ۳۰٪ بعدی در گروه `Medium` و بقیه در گروه `Low` قرار می‌گیرن. این درصدها هم فعلاً یک قاعده اولیه برای نمایش خروجی هستن.

## ذخیره خروجی در PostgreSQL

نتایج در جدول `lead_scores` ذخیره می‌شن. برای هر لید، احتمال خرید، حاشیه سود، امتیاز اولویت، سطح اولویت، نسخه مدل و زمان امتیازدهی نگهداری می‌شه.

در هر اجرای `score.py`، ابتدا جدول `lead_scores` با دستور `TRUNCATE` خالی و سپس نتایج جدید با `INSERT` ذخیره می‌شن. هر دو عملیات در یک تراکنش انجام می‌شن؛ بنابراین در صورت خطا پیش از `COMMIT`، امکان بازگشت تغییرات وجود داره. جدول فقط نتایج آخرین اجرای موفق رو نگه می‌داره و تاریخچه اجراهای قبلی ذخیره نمی‌شه.

برای بررسی تعداد لیدهای ذخیره‌شده:

```bash
docker-compose exec -T db psql -U admin -d leads_db -c "SELECT COUNT(*) FROM lead_scores;"
```

برای دیدن توزیع اولویت‌ها:

```bash
docker-compose exec -T db psql -U admin -d leads_db -c "SELECT priority, COUNT(*) FROM lead_scores GROUP BY priority ORDER BY priority;"
```

و برای مشاهده چند لید اول:

```bash
docker-compose exec -T db psql -U admin -d leads_db -c "SELECT lead_id, purchase_probability, expected_margin, priority_score, priority FROM lead_scores ORDER BY priority_score DESC LIMIT 10;"
```

در صورت اجرای موفق روی کل داده، انتظار داریم ۵۰٬۰۰۰ لید یکتا در جدول وجود داشته باشه. این تعداد باید بعد از اجرا با خروجی واقعی دیتابیس بررسی بشه.

## بررسی احتمال Leakage در ستون تماس

ستون `Incoming Call Last 24h` در مدل اصلی استفاده نشده، چون زمان ثبت تماس نسبت به زمان ایجاد لید و زمان تصمیم‌گیری برای اولویت‌بندی مشخص نیست. اگر تماس بعد از ایجاد لید و به‌ویژه بعد از زمان تصمیم‌گیری برای تماس توسط تیم Telesales ثبت شده باشه، استفاده از این ستون ممکنه باعث **Data Leakage** بشه؛ یعنی مدل از اطلاعاتی استفاده کنه که در زمان پیش‌بینی واقعاً در دسترس نبوده.

از طرف دیگه، اگر این ستون صرفاً تماس ورودی مشتری **قبل از زمان امتیازدهی** رو نشون بده و در محیط عملیاتی هم همون موقع در دسترس باشه، لزوماً Leakage نیست و می‌تونه Feature معتبری باشه. بنابراین حذف فعلی یک تصمیم احتیاطیه، نه اثبات وجود Leakage؛ **تصمیم نهایی بعد از شفاف‌شدن تعریف ستون، منبع تماس و ترتیب زمانی رویدادها گرفته می‌شه.**

برای بررسی حساسیت عملکرد مدل به این ستون، یک آزمایش جداگانه با تنظیمات ثابت Logistic Regression و تقسیم یکسان داده‌ها اجرا می‌کنیم:

```bash
docker-compose run --rm pipeline python src/call_feature_ablation.py
```

خروجی مقایسه در `reports/call_feature_ablation.csv` ذخیره می‌شه. بهترشدن متریک‌ها با اضافه‌شدن ستون به‌تنهایی نشون نمی‌ده که استفاده از اون مجازه؛ اعتبار زمانی Feature باید جداگانه تأیید بشه. این آزمایش مدل نهایی و جدول امتیازدهی رو تغییر نمی‌ده.
